The problem

Seats open at 3 a.m. and nobody tells you

At Rutgers a full section stays full until someone drops it. Most courses have no waitlist, and nothing emails you when a seat frees up. The seat goes to whoever happens to be refreshing WebReg at that moment.

So students refresh manually, for days. The window is short — a section that opens at 3 a.m. during registration week is usually gone by morning. The whole product is: notice the moment it happens, and remove every second of friction between the notification and the registration form.

Architecture

One detection engine, several front doors

The piece that decides a seat opened knows nothing about Discord, or the web, or push notifications. It emits an event; whatever is listening delivers it. That separation is the main structural change from V1, where detection and Discord API calls were interleaved inside the same function — which is why the bot could not grow a second surface without a rewrite.

Design decisions

The forks, and which way I went

Each of these had a defensible alternative. These are the ones I'd expect to defend.

Detect changes by diffing, not by re-checking

The naive version: each tick, ask "is this section open?" and notify if yes. That re-fires every tick for as long as the seat stays open, so V1 suppressed the noise with a ten-minute cooldown tracked per (user, section) pair.

What I did instead: keep the previous set of open indexes and compute new − previous. A section that was already open isn't in the difference, so it emits nothing. The cooldown table disappears — and so does the restart bug it caused, where the in-memory timers were lost and every watcher got re-notified for seats that had been open for hours.

What it costs: you hold one set in memory and lose a tick of history on restart. That's a much smaller problem than the one it replaces.

Split the data by how fast it changes

Titles, professors and meeting times change essentially never during a term. Open/closed changes constantly. Fetching them together means re-downloading the entire catalogue to learn one boolean per section.

So they're on different schedules: the catalogue is built once a day into a static file behind a CDN, and only the open-set is polled. This is why the demo has no database. The slow data is a file; the fast data is small enough to diff in memory — 27 ms to parse the catalogue once, 2 ms per diff. Adding Postgres here would introduce a network hop to solve a problem that doesn't exist yet.

It starts existing the moment state has to outlive a page load, which is exactly where the roadmap picks up.

Let the upstream cache set the poll rate

V1 polled once a second, on the assumption that faster is better. The endpoint sends Cache-Control: max-age=30 — any cache between you and Rutgers may serve data up to thirty seconds old, so twenty-nine of every thirty requests could not have returned news.

Polling at 30 s cuts request volume by 30× with no meaningful loss in detection latency. I checked whether conditional requests could do better: the endpoint sends an ETag but ignores If-None-Match, returning a full body regardless.

The general point — read the response headers before designing around an assumption about the server.

Invert the lookup before fan-out needs it

V1 looped over every user each tick and intersected their watchlist against the open set: O(users) per tick whether or not anything had happened.

The right shape is an index → {watchers} map. Intersect the newly-opened set against its keys once and you touch only users who actually have news, so the cost becomes O(newly opened) — usually zero.

At current scale neither approach is measurably different. It matters the first time the thing gets popular, and it is far cheaper to build now than to retrofit under load.

Make the CORS question moot instead of answering it

The Schedule of Classes API sends no Access-Control-Allow-Origin, so a browser cannot call it from a page. The obvious fix is a proxy that adds the header. The better fix is a proxy that removes the question: running it as a Pages Function on the same origin as the site means no cross-origin request is ever made.

The proxy also caches at the edge, so a hundred simultaneous visitors produce one request to Rutgers per window rather than a hundred. Being a well-behaved client of someone else's infrastructure is a design requirement here, not a nicety — the alternative is getting blocked.

Key every persisted record to a term

This one came out of a real bug. Rutgers recycles index numbers between terms. 3,059 index numbers from Spring 2025 also appear in Fall 2026, attached to entirely different courses.

V1 stored its last-opened history as a flat index → timestamp CSV with no term column. At every rollover, existing rows silently became wrong: index 10052 kept its old timestamp while now referring to a different class. Nothing errored. The file looked fine. It was simply lying.

Anything persisted is now keyed by (term, campus, index). It's also why the V1 history wasn't migrated — there is no way to interpret it after the fact.

Refuse to handle credentials

There's an obvious "better" product here: register for the student automatically. It requires their NetID and password, which means storing university credentials for thousands of people.

That's an enormous liability, and the fastest possible way to get the project shut down by the university. So the boundary is fixed: RU SnipeZ detects and notifies, the link opens WebReg with the index pre-filled, and the student authenticates through CAS themselves. It costs a few seconds of user time and eliminates the entire credential-handling surface.

Reliability

What breaks, and what happens when it does

V1 had exactly one try/except in the whole codebase. A single network blip would stop the monitoring loop while the bot stayed online and responsive — silently monitoring nothing, with no way for anyone to tell.

About

I built this because I couldn't get into my classes

Rutgers course registration works like this: you get an enrollment appointment, the sections you need are already full, and you spend the next two weeks refreshing WebReg hoping somebody drops.

There's no waitlist for most courses. Nothing notifies you. The seat goes to whoever is looking at the right moment — which means the students who get their classes are the ones with time to sit and refresh.

The first version

I built RU SnipeZ as a Discord bot. You'd run /snipe 10052, it would watch that index, and the moment the seat opened you'd get a DM with a registration link that already had the index filled in — so you weren't typing a five-digit number while the seat disappeared.

It ran for a student Discord community through 2024, with slash commands for adding, listing and clearing watches, and a logging system so I could see what was actually being used. People got classes with it.

What I found when I went back and measured

This is the part I think is actually worth telling. The bot worked well enough that nobody complained, and it was still wrong in four ways I could only see by re-examining it properly:

  • It polled once a second because I assumed faster meant better. The endpoint caches for thirty seconds — twenty-nine out of every thirty requests were incapable of returning news.
  • It scraped course data with a headless browser across fifteen pages, about two and a half minutes per run, because I hadn't found the JSON endpoint that the page itself was calling. One request replaces the entire pipeline.
  • A single network error stopped the monitoring loop permanently. The bot stayed online and kept answering commands while monitoring nothing. Nobody — including me — had any way to tell.
  • Its history was quietly corrupt. It stored last-opened times keyed only by index, and Rutgers recycles index numbers between terms. Every rollover, the old rows started describing different courses. The file never errored; it just stopped being true.

None of those were visible from outside. That's the lesson I actually took from this project: "it works" and "it's correct" are different claims, and only one of them survives measurement.

The rebuild

V2 separates the part that detects an opening from the part that tells you about it. The detection engine emits an event; delivery is a plug. That's what makes a web interface possible at all without touching the monitoring logic, and it's what will let push notifications, Telegram or SMS be added later as sinks rather than rewrites.

The How it works page walks through the specific decisions and the tradeoffs behind them.

What this page is

This is the same engine as the Discord bot, with a web interface instead of a chat one. When you press Watch and the alert card appears, that's the same notification the bot sends to a DM — same fields, same pre-filled WebReg link, same one-click flow. The only difference is the surface it arrives on.

Everything on the Monitor tab is live: the catalogue is rebuilt daily from the Rutgers API, and open/closed status refreshes every thirty seconds against the real endpoint. Nothing is mocked.

Honest limitation

This demo watches sections only while the tab is open, because the browser is doing the polling. Your watchlist lives in your own browser and never leaves it — which also means it doesn't follow you to another device. Background alerts that reach you with the tab closed need an always-on server, and that's the next milestone rather than something this page does today. The Discord bot didn't have that limitation; this surface doesn't have it yet.

Things worth knowing before relying on it

  • A section badged SPN needs a special permission number from the department — an open seat there isn't registrable on its own. That's 24% of New Brunswick sections, so it materially changes which alerts are worth acting on.
  • A section badged XL is cross-listed under a second department code with its own index. The two open and close independently, so it's usually worth watching both.
  • Open/closed reflects what the university's own endpoint reports, cached up to thirty seconds — as current as the Schedule of Classes website itself.
  • Outside registration periods most sections sit still, so the activity feed will mostly log quiet polls. That's the system working, not a fault.

Where it deliberately stops

RU SnipeZ notifies. It does not register for you, and it never asks for, stores, or transmits a NetID or password. You sign in to WebReg through CAS yourself, exactly as you normally would — the link only saves you from typing the index.

That's a design constraint rather than an unfinished feature. Automating registration would mean holding university credentials for thousands of students, which is both a serious liability and the quickest way to get a project like this shut down. It reads the same public endpoints the Schedule of Classes website reads, caches at the edge so one request serves every visitor, and polls no faster than the university's own cache headers invite.

What's next

An always-on poller so alerts fire with the tab closed, then Web Push as the first real channel. After that: per-term last-opened history, a prompt to watch both halves of a cross-listed pair, and watching by core requirement rather than by index — so an underclassman can ask for "any open section that satisfies my remaining Historical Analysis credit" without knowing which course they want.
