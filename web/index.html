The problem

Seats open at 3 a.m. and nobody tells you

At Rutgers, a full section stays full until someone drops it. Most courses have no waitlist, and nothing notifies you when a seat frees up. The seat goes to whoever happens to be refreshing WebReg at that moment.

That window is short. A popular section that opens overnight during registration week is usually gone by morning. RU SnipeZ closes two gaps: noticing the opening within seconds, and removing every keystroke between the alert and a submitted registration.

Architecture

One detection engine, several front doors

The component that decides a seat opened knows nothing about Discord, the web, or push notifications. It emits an event, and whichever surfaces are listening deliver it. Adding a channel means adding a subscriber, not touching the monitoring logic.

Design decisions

The choices that shape it

Each of these had a reasonable alternative. These are the ones worth defending.

Detection is a set difference, not a repeated question

Each cycle produces the set of currently open indexes. The engine computes new − previous and treats only that difference as news. A section that was already open is not in the difference, so it produces no event.

That single property removes a whole category of problems. There is no per-user cooldown timer to maintain, no duplicate alert when a seat sits open for an hour, and no burst of stale notifications after a restart. Correctness comes from the shape of the computation rather than from suppression rules layered on top of it.

Data is split by how fast it changes

Course titles, professors and meeting times are effectively fixed for a term. Open and closed status changes continuously. Treating them as one dataset would mean transferring the entire catalogue to learn one boolean per section.

So they run on separate schedules. The catalogue is compiled once a day into a static file behind a CDN, and only the open set is polled. The result is that a page load parses the full catalogue in 27 ms and each subsequent check costs 2 ms, which is why this surface needs no database at all. Persistence enters the design at exactly the point state has to outlive a page load, and not before.

The poll cadence comes from the upstream contract

The Schedule of Classes endpoint declares Cache-Control: max-age=30. Any cache between the client and the university may serve a response up to thirty seconds old, so a faster poll cannot surface anything a thirty second poll would miss.

Matching that cadence keeps detection latency at its real floor while making the smallest possible demand on university infrastructure. Conditional requests were evaluated as a further optimisation: the endpoint sends an ETag but does not honour If-None-Match, so they return a full body and save nothing.

Fan-out runs through an inverted index

Watches are stored as index → {watchers} rather than user → {watches}. When a cycle produces newly opened indexes, the engine intersects that small set against the map keys once and touches only the users who actually have news.

Cost scales with the number of openings, which is usually zero, instead of with the number of subscribers. The structure holds whether five people are watching or five thousand, so growth does not require revisiting the hot path.

The proxy shares an origin with the page

The Schedule of Classes API sends no cross-origin headers, so a browser cannot call it directly. Running the proxy as an edge function on the same origin as the site means no cross-origin request is ever made, which removes the class of problem rather than configuring around it.

The same layer caches responses at the edge, so a hundred people watching the page produce one upstream request per window instead of a hundred. Being a light client of someone else's infrastructure is a functional requirement here, not a courtesy.

Trust the catalogue, not the query parameters

Two of the upstream endpoints accept parameters they then ignore. The catalogue endpoint takes a subject and returns the whole campus regardless, and the open-sections endpoint takes a campus and returns every open index university wide, all 11,444 of them, whichever campus you ask for.

So campus scoping happens here rather than upstream: the open set is intersected against the catalogue actually loaded, which is the only authoritative statement of what belongs to a campus. Counting the raw response instead would report New Brunswick's total on the Camden page. Filtering on the client is normally a smell, and it is the correct answer when the server's filter does not exist.

Every stored record is keyed to a term

Rutgers reuses index numbers between terms. 3,059 of the index numbers valid in one recent term are also valid in another, attached to entirely different courses. An index alone is not a stable identifier for anything.

So the composite key is (term, campus, index) everywhere state is written. Historical records stay interpretable across a rollover, and a query can never silently return a row that describes a different class than the one it was written for.

Credentials never enter the system

A tempting extension is to complete the registration automatically. Doing so requires the student's NetID and password, which means holding university credentials on behalf of thousands of people.

The boundary is fixed instead: RU SnipeZ detects the opening and delivers the alert, the link opens WebReg with the index already filled in, and the student authenticates through CAS themselves. The cost is a few seconds of user time. The benefit is that there is no credential store to secure, breach, or be trusted with.

Reliability

Behaviour under failure

A monitor that stops monitoring without saying so is worse than no monitor, because people rely on its silence. Every failure path is therefore visible rather than quiet.

About

Get the class, without living in WebReg

Rutgers course registration rewards whoever happens to be watching. Sections fill instantly, most have no waitlist, and a seat that frees up at 3 a.m. goes to whoever refreshed at 3:01.

RU SnipeZ watches for you. Pick the sections you need, and the moment a seat opens you get an alert with a WebReg link that already has the index filled in. No refreshing, no typing a five digit number while the seat disappears.

Every section offered in New Brunswick, Newark and Camden, with professors, meeting times, room assignments, core requirement codes and registration restrictions. The catalogue rebuilds daily, and open status refreshes every thirty seconds against the university's own endpoint.

Two ways to use it

On Discord, run /snipe 10052 and the bot watches that index and sends you a direct message the moment it opens, with the registration button attached. /check lists what you are watching, /remove drops one, /clear empties the list.

On this page, search for a class and press Watch. The alert card you see is the same notification the bot delivers, with the same fields and the same one click path into WebReg. The only difference is the surface it arrives on.

Using this page

  • Search by course name, professor, course code or index number. Press / to jump to the search box from anywhere.
  • Filter by campus, meeting day, building location, or core requirement code, then sort by best match, open seats, course code or section count.
  • Click any section row to expand it for exam date, prerequisites, full meeting pattern and the department synopsis.
  • Press Watch to add a section, then enable desktop alerts so openings reach you outside the tab.
  • Use Copy link to this view to share a URL that reproduces your exact search and filters.

What the badges mean

  • SPN The section requires a special permission number from the department, so an open seat is not registrable without approval first. This applies to 24% of New Brunswick sections, and knowing in advance changes which alerts are worth acting on.
  • XL The section is cross-listed under a second department code with its own index number. The two indexes have separate seat pools and open independently, so watching both roughly doubles your chances. RU SnipeZ offers to add the twin when you watch either one.
About this page specifically

The web surface watches while the tab is open, and your watchlist is stored in your own browser rather than on a server, so it stays private to you and does not follow you between devices. For alerts that reach you with everything closed, the Discord bot is the channel to use today. An always-on web poller with push notifications is the next thing being built.

Where it stops

RU SnipeZ notifies. It does not register on your behalf, and it never asks for, stores or transmits a NetID or password. You sign in to WebReg through CAS yourself, exactly as you always would, and the link simply saves you from typing the index.

That boundary is deliberate. Automating the registration itself would mean holding university credentials for thousands of students, which is a liability no convenience justifies. RU SnipeZ reads the same public endpoints the Schedule of Classes website reads, caches at the edge so many visitors cost one request, and checks no more often than the university's own cache policy invites.

What is coming

An always-on poller so web alerts arrive with the tab closed, then Web Push as the first background channel. After that: per term history showing when a section last opened and how long it stayed open, and watching by core requirement rather than by index, so a student can ask for any open section that satisfies a remaining Historical Analysis credit without knowing which course they want.
